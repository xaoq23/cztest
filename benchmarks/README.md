# 编译与体积基准

「比 gtest 轻」这种话，没有数字就是营销。这里有数字，也有跑出这些数字的脚本。

## 测什么

三个框架拿到**同样的用例**：

| 变体 | 内容 |
| --- | --- |
| plain | 1000 个空用例 |
| mocks | 1000 个用例，每个带一个 mock 方法和一条期望（doctest 没有 mock，跳过） |

测三件事：

| 指标 | 怎么测 |
| --- | --- |
| 编译时间 | 编译那一个装着全部用例的翻译单元，取 3 次的中位数 |
| 二进制大小 | 链接之后的可执行文件 |
| 运行时间 | 跑测试进程，取 3 次的中位数（进程启动本身也要几十毫秒） |

## 怎么跑

```bash
python benchmarks/run.py                      # 1000 个用例，3 次
python benchmarks/run.py --cases 200 --runs 5
python benchmarks/run.py --compiler clang++
```

脚本会把 GoogleTest 和 doctest 下载到 `benchmarks/.deps/`（**不装到系统里** ✓），用同一个
编译器把它们编成静态库 ✗ —— 所以三个框架是在同一把尺子下量的 ✓。

需要的工具：一个 C++ 编译器、`git`、`ar` ✗ —— 没有 cmake ✗。

## 数字

环境：Windows 11，MinGW g++ 16.2.0（ucrt64），`-O2`，1000 个用例，3 次取中位数。

| 变体 | 编译时间 | 二进制大小 | 运行时间 |
| --- | --- | --- | --- |
| cztest / plain | 15.2 s | 936 kB | 19 ms |
| cztest / mocks | 25.6 s | 1469 kB | 20 ms |
| gtest / plain | 38.3 s | 4984 kB | 44 ms |
| gtest / mocks | 38.4 s | 5769 kB | 49 ms |
| doctest / plain | 10.2 s | 1409 kB | 20 ms |

### 这些数字说明什么

**比 gtest 轻 ✓** —— 编译快 1.5 到 2.5 倍 ✓，二进制小 3 到 4 倍 ✓，跑起来也快 ✓。
差别最大的地方是**每个用例的编译成本** ✓：

| | 每个用例的编译成本 |
| --- | --- |
| cztest | 约 3 ms |
| gtest | 约 7 ms（`-O0`）/ 23 ms（`-O2`） |

**比 doctest 重 ✓** —— 这是应该的 ✓：cztest 有 mock ✓、有运行器 ✓、有过滤器 ✓、
有 JUnit 报告 ✓，doctest 都没有 ✓。

**cztest 的固定成本更高 ✓** —— 空测试的翻译单元要 1.8 秒 ✓，gtest 只要 0.9 秒 ✓。
两个原因 ✓：

1. 头文件里带了 `<chrono>` `<sstream>` `<fstream>` 这些不便宜的标准头 ✓；
2. **gtest 的运行器在预编译的库里 ✓，而 cztest 的运行器在你的翻译单元里编译 ✓**
   —— 这就是「纯头文件」的代价 ✓。

第二个原因是可以换的：gtest 用两个库换来更快的编译 ✓，cztest 用一个 `-I` 换来零依赖 ✓。
这是同一个取舍的两面 ✓。

### 为什么每个用例只花 3 毫秒

一开始不是这样 ✗：每个用例的注册体是一个 `std::function` ✗，
而 `std::function` 从 lambda 构造时**每个 lambda 都会生成一个自己的类** ✗ ——
编译器要为每个用例生成一次 ✗，**每个用例 12.8 毫秒** ✗。

改成函数指针之后 ✓，每个用例的注册体不再有类型 ✗，成本掉到 3 毫秒 ✓。

## 复现

数字依赖机器 ✗，所以上面那张表只是一次测量的结果 ✓。在自己的机器上跑脚本 ✓
就能得到自己的数字 ✓ —— 这也是脚本存在的意义 ✓。
